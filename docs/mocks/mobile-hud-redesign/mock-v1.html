Mobile HUD — three directions

Design exploration only, nothing implemented. All three put the board full-bleed behind a floating HUD, and all three keep fixed slots: a control that is unavailable is dimmed in place, never unmounted, so nothing reflows between turn states. Measurements are against a 390×844 phone.

What we're fixing. The desktop rail rules are currently applying on phones:
  • Board renders 108×105 px — 3.4% of the screen (it was 30.7% before the desktop redesign).
  • Top chrome eats 109 px before the board starts; the stage gets 132 px.
  • Action buttons inherit the rail's column flex, so widths come out ragged: 148 / 88 / 129 / 82 / 61 / 82 px.
  • Everything is stacked in one scrolling column, so the board competes with the controls for the same axis.

Resources hug the left edge, dev cards the right, actions along the bottom — the layout you described. Board reclaims the whole screen behind them. Most literal, most information on screen at once.

Recommendation

B, with A's dev rail available as an option. Resources are what you read constantly while deciding a move, so they earn a permanent rail; dev cards get consulted a few times a game, so a count chip with a tap-to-open tray is a fair trade for the whole right edge. The thumb cluster also puts Roll and End turn — the two highest-frequency taps in the game — where a one-handed grip actually lands, which none of the current layouts do.

Rules all three follow

  • Fixed slots. A resource you hold none of stays as a dashed placeholder; an unaffordable build button dims in place. Nothing mounts or unmounts mid-turn, so nothing reflows.
  • Board never resizes. The HUD floats above a full-bleed board instead of sharing a column with it, so board size is independent of what the HUD is showing.
  • Safe areas respected. Bottom bars pad by env(safe-area-inset-bottom), the top bar by env(safe-area-inset-top).
  • Landscape degrades cleanly. The bottom bar becomes a right rail and the board keeps the rest — the current layout cannot do this at all.

Open questions

  • Should the left rail show a resource you hold none of? Drawn here as a dashed slot to keep positions fixed; the alternative is a shorter rail that shifts as your hand changes.
  • Where do the dice belong? Placed differently in each mock on purpose — today they float in open water far from the roll button.
  • Public-hands mode shows four hands at once. Does it replace the left rail, or open as a sheet?
  • Does the board need pan/pinch once the HUD overlaps its edges, or is a slightly smaller board with clear margins better?
